# How SHAZA's three data environments coexist

*Design note. Follows `docs/charter.md` sections 3, 4 and 5. Written while SHAZA has no
farmland, which is exactly when this has to be settled.*

---

## 1. The three environments are two axes, not three buckets

The charter names three environments: **A — real external data**, **B — historical data**,
**C — synthetic data**. Read as three storage areas, that design does not survive contact with
the data already in the database.

The 21,930 rows SHAZA holds today came from the Open-Meteo historical archive. That is an
external API, so it is Environment A. It is also two years of past daily weather used for
trends and correlation, so it is Environment B. The same rows are both. If A and B were
separate stores, those rows would have to be duplicated or arbitrarily assigned, and the two
copies would drift.

A and B are not separable because they are not the same kind of distinction. The three
environments collapse two independent axes.

**Axis 1 — origin.** Where the value came from. This is `SourceKind`:

| Value | Meaning | Environment |
| --- | --- | --- |
| `external_api` | fetched live from a third party | A |
| `public_dataset` | bulk download (FAOSTAT, World Bank, NISR) | A |
| `synthetic` | generated by SHAZA's own simulator | C |
| `field_observation` | measured by SHAZA on real land | stage 9 |

**Axis 2 — claim.** What the number asserts. This is `Provenance`: `observed`, `reanalysis`,
`forecast`, `simulated`, `derived`.

Origin and claim are genuinely independent. An external API can deliver a reanalysis, a
forecast, or a station measurement. Both axes already exist in `backend/app/models/provenance.py`.

**Environment B is on neither axis.** Historical data is not an origin and not a claim. It is a
time window over data SHAZA already holds, plus a way of working with it. "Historical" means
`observed_on` is in the past and the question being asked is about trend rather than state.

So:

```text
A = rows whose source kind is external_api or public_dataset
C = rows whose source kind is synthetic
B = a query over A, filtered by date, plus the analysis done with the result
```

Two storage environments. One of them has an analysis mode built on top of it. This is the
whole design, and SHAZA already implements most of it.

## 2. One fact table, segregated by source

A and C share a table. `Observation` stores one value for one variable at one location on one
day, with a required `provenance` column declared before `value`.

The simulator does not get its own table or its own database. It gets a `Source` row with
`kind = synthetic`, and it writes `Observation` rows with `provenance = simulated` pointing at
that source. Coexistence is then automatic, and so is the guarantee that matters: there is no
path that reads a value without also reading what kind of claim it is.

```text
  Open-Meteo / ERA5  --+
  FAOSTAT            --|                      +-- kind, attribution, licence
  NASA POWER         --+-->  sources  --------+
  Synthetic Farm     --|                      +-- one row per origin
  SHAZA field (st. 9) --+        |
                                v
                          observations
                     (provenance, maturity,
                      uncertainty, value)
```

The alternative, a separate synthetic database, is worse in a way that is not obvious at first.
It makes contamination impossible, but it also makes **comparison** impossible. The entire point
of the digital twin in charter section 6 is to put SHAZA's simulation next to reality and measure
the gap. If they live in different stores, that comparison is an export-and-join chore forever.
In one table it is a self join on `(location_id, variable, observed_on)` across two `source_id`
values. Keep them together and guard the queries.

## 3. What has to be added

**Two enum values, before they are needed.**

- `SourceKind.MODEL_OUTPUT` — a SHAZA model version, registered as a source. The `sources` table
  is already an experiment registry: slug, name, url, notes, created_at. Register each model
  version there rather than building a second tracking system beside it.
- `Provenance.PREDICTED` — output of a SHAZA model. Today a prediction has nowhere honest to go.
  `forecast` is somebody else's prediction, and `derived` is arithmetic over stored values.
  Folding a regression output into `derived` puts a unit conversion and a guess in the same
  bucket, which is the exact blur the enum exists to prevent.

**Three entities for the Synthetic Farm.** `Observation` cannot express "a hypothetical farm
growing Irish potato, planted on 15 October". It has no crop, no farm, and no notion of a
scenario. The simulator needs its own inputs, which then produce ordinary labelled observations:

```text
SyntheticFarm   hypothetical. references a real Location for its climate baseline,
                plus crop, soil type, area, planting date.

Scenario        a named set of deltas against a baseline:
                rainfall -20%, temperature +1.5C, planting date +14 days.

ScenarioRun     one execution: scenario, seed, code version, run timestamp.
                Emits Observation rows with provenance = simulated.
```

`ScenarioRun` is what keeps a simulated number auditable. Without the seed and the code version,
a synthetic series is unreproducible, and an unreproducible simulation is not research.

Note that a scenario perturbs a **real** baseline. Musanze's simulated rainfall starts from
Musanze's actual ERA5 record. The output is still `simulated`, because the perturbation is
invented, and the lineage back to the baseline lives in `ScenarioRun`.

## 4. Where the three environments actually converge

`Observation` is daily and has no crop. Three things SHAZA needs do not fit it:

- FAOSTAT and NISR crop yield: per location, per **crop**, per **season**
- the Synthetic Farm's simulated harvest: the same shape
- a real harvest from SHAZA land at stage 9: the same shape again

That shared shape is the outcome variable SHAZA currently does not have. Weather is all input;
there is nothing yet to predict. A second fact table is needed, roughly:

```text
CropOutcome   location (or synthetic_farm), crop, season, outcome variable
              (yield / production / area), value, unit,
              source_id, provenance, uncertainty
```

This table is the one that pays off. The same row shape holds a FAOSTAT yield
(`public_dataset` / `observed`), a simulated yield (`synthetic` / `simulated`), a model's
prediction (`model_output` / `predicted`), and eventually a real SHAZA harvest
(`field_observation` / `observed`). Stage 9's central question, *did SHAZA's prediction match
reality*, becomes one query over one table rather than a research project of its own.

Ingesting an outcome dataset is therefore a deliberate Stage 2 goal, not more weather.

## 5. Query rules

One table means a careless query mixes environments. Three rules:

1. **No bare `select(Observation)`.** Every read states its environment. The default excludes
   `synthetic` and `model_output`; including them is an explicit opt-in on the caller's side.
2. **A series never spans sources.** Group by `(variable, provenance, source_id)`. One series,
   one attribution.
3. **Mixing is opt-in and visible.** A response containing more than one source kind says so,
   and the UI renders the distinction. Comparison is a feature; accidental merging is a defect.

Rule 1 belongs in a test, not a convention. A convention is a thing a tired person forgets at
11pm; a failing test is not.

## 6. Two defects this exposes in the current API

Both are in `backend/app/routers/observations.py`, both are cheap now and expensive later.

**Grouping omits the source.** Series are grouped by `(variable, provenance)` and the source is
then read off `observations[0]`. With one source in the database this is correct. Add a second
reanalysis source in Stage 2, say NASA POWER alongside Open-Meteo, and both collapse into one
series carrying whichever source happened to sort first. The other source's rows are then
published under the wrong attribution, and attribution is a licence condition, not a courtesy.
Add `source_id` to the grouping key.

**No environment filter.** The endpoint selects every row for the location and date range. Once
the simulator writes to the same table, synthetic series appear in ordinary data responses by
default. They would be correctly labelled, so the hard rule holds, but the default is backwards:
the simulator's output should be absent unless asked for.

## 7. What this design buys

When land arrives, nothing is rebuilt. A real thermometer in Musanze registers as a source with
`kind = field_observation` and writes `provenance = observed` rows into the same table that
already holds two years of `reanalysis` for the same point. The first real experiment, *how far
is ERA5 from the actual field*, is a query against data SHAZA is already collecting today.

That experiment exists because the reanalysis was never mislabelled as observed. Most of the
value in this architecture comes from that one decision, already made.
